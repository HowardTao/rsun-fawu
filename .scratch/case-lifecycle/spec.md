# 案件登记、立项、办理、履行与关闭分规格

Status: ready-for-agent

更新日期：2026-10-22。父规格：[法务系统完整重建总规格](../fawu-rebuild/spec.md)。本分规格是首个案件端到端里程碑，首期仍须交付十组完整业务。

规格已发布，相关核验项是依赖用例实施的前置条件。具体字段、状态全集和平台契约未由本规格的发布状态视为核验通过；核验工作见[共用清单](../fawu-rebuild/verification-checklist.md)。

## Problem Statement

法务人员与业务经办人需要从案件登记到最终办结持续办理案件，并明确当前责任、实际诉讼程序、每次内部审批和剩余履行义务。旧实现中部分审批回调直接更新案件阶段，独立关闭方法未在方法内检查履行余额，多个历史状态和关联依赖分散在页面、日志和业务记录中。

重建需要贯彻用户已确认的新规则：程序事实与内部审批分别表达；审理结案与执行完毕分开；义务未明确处理完毕不关闭。同时必须保留既有审批、案件历史、律师委托、附件以及切换前在途申请。直接照搬旧回调或页面状态不足以满足这些要求。

## Solution

提供从直接登记、提交立项、退回补正重提、正式立项、阶段办理和责任移交，到审理结案、履行跟踪及授权关闭的完整链路。每次业务申请独立记录审批资料、状态和历史；程序阶段按可核实的程序事实维护，阶段内进度独立表达。

以自定义角色的操作与对应数据范围控制每个用例。案件提交前有一位主责承办人，经办与协作关系另行记录，移交后按当前关系重新判定访问。审批人在既有平台办理，新法务发起、查询并提供跳转；受理不明、重复及迟到结果可核对，不误改当前事实。

审理结案后继续管理应收应付和其他履行事项；特殊事件保留人工记录及依据，不自动归零或关闭。全部所需义务经确认处理完毕后，授权人员记录理由和依据并关闭；无需执行的案件在审结后核对办结。历史与旧在途按总规格的保留、受限办理和唯一处理链原则衔接。

## User Stories

职责名称是使用场景，不是固定权限角色。各操作还必须有对应数据范围及合法业务前提。

1. **C-01** 作为有案件登记权限的人员，我希望直接录入案件，以便先保存待立项业务资料。
2. **C-02** 作为登记人员，我希望记录当前有效的案件类型、当事人、案发组织、案情和材料，以便形成可提交的案件依据。
3. **C-03** 作为立项发起人员，我希望提交前明确一位主责承办人，并另列经办与协作人员，以便当前责任与本人相关范围可判定。
4. **C-04** 作为登记人员，我希望登记人与主责可以不同，以便业务录入和法务主责分工不必合并。
5. **C-05** 作为案件使用者，我希望按角色操作和对应范围查询列表、详情及关联信息，以便只能执行已获授权的访问。
6. **C-06** 作为兼有全集团查看和本人修改角色的人员，我希望查看全部授权案件但只修改本人相关范围，以便角色组合不扩大修改权。
7. **C-07** 作为有立项发起权限的人员，我希望提交案件资料到既有审批平台，以便通过后正式立项。
8. **C-08** 作为立项发起人员，我希望缺少主责或核定必填资料时提交被拒绝，以便不产生无效外部申请。
9. **C-09** 作为案件参与人员，我希望查看每次提交的固定资料及对应审批历史，以便知道每次实际审批的内容。
10. **C-10** 作为有资料维护权限的人员，我希望审批期间不能修改该次提交资料，以便提交版本保持可核对。
11. **C-11** 作为立项发起人员，我希望通过平台支持的退回或撤回后再补正，以便不会在审批中悄悄替换资料。
12. **C-12** 作为补正人员，我希望在同一案件修改资料并再次提交，以便不创建重复案件。
13. **C-13** 作为案件参与人员，我希望保留每次申请与处理历史，以便退回重提后仍能追溯原申请。
14. **C-14** 作为业务决定不再继续的授权人员，我希望保留案件记录并明确标记终止，以便与正式立项、关闭分别理解。
15. **C-15** 作为发起人员，我希望受理回执不明时看到待确认并核对实例，以便不盲目再次创建申请。
16. **C-16** 作为有权限的案件使用者，我希望查看审批状态、结果、历史并跳转既有平台，以便审批仍按原平台规则办理。
17. **C-17** 作为案件承办人，我希望只有有效立项审批通过才正式立项，以便内部立项结果可确认。
18. **C-18** 作为案件承办人，我希望重复立项结果不会重复生成目标计划、关联或通知，以便重传不重复产生业务效果。
19. **C-19** 作为案件承办人，我希望同时看到每次审批状态、程序阶段及阶段内进度，以便不同业务含义清楚表达。
20. **C-20** 作为有程序维护权限的人员，我希望根据核实的法院或仲裁程序事实更新阶段并保留依据，以便准确表达实际程序。
21. **C-21** 作为案件使用者，我希望法院已受理二审时看到二审，内部上诉申请仍可以审批中，以便实际程序与内部审批各自表达。
22. **C-22** 作为有进展维护权限的人员，我希望记录阶段进展、目标、下一步计划及材料，以便主责持续跟进案件。
23. **C-23** 作为案件使用者，我希望旧申请迟到结果不会覆盖新申请或已经核实的程序事实，以便当前信息不倒退。
24. **C-24** 作为有主责移交权限的人员，我希望指定新主责后生效，并记录原主责、新主责、原因和时间，以便交接可追溯。
25. **C-25** 作为新主责承办人，我希望移交后按当前关系和角色获得相应访问，以便承担后续办理职责。
26. **C-26** 作为原主责承办人，我希望移交后按当前关系重新判定访问，以便不因过去承办而自动保留权限。
27. **C-27** 作为仍参与案件的原主责，我希望按当前经办、协作或其他角色授权访问，以便移交不错误抹去其他有效授权。
28. **C-28** 作为有结案维护权限的人员，我希望记录审理结案结果、日期和依据，以便核对审理情况与后续义务。
29. **C-29** 作为主责承办人，我希望审结后仍能跟踪未收、未付及其他履行事项，以便不会因审结漏掉剩余义务。
30. **C-30** 作为有履行维护权限的人员，我希望维护收付、履行事项、期限和处理依据，以便办结核对有可解释的结果。
31. **C-31** 作为有关闭权限的人员，我希望未处理义务存在或处置不明时关闭被拒绝，以便案件保持未办结。
32. **C-32** 作为有关闭权限的人员，我希望全部所需义务处理完毕后记录关闭理由和依据，以便无需新增正常关闭审批即可确认办结。
33. **C-33** 作为有关闭权限的人员，我希望无需执行的案件在审结后核对办结，以便不虚构不存在的收付或执行流程。
34. **C-34** 作为案件办理人员，我希望维护和解、中止、特殊结案等已有人工记录及附件，以便保留特殊事件及后续安排。
35. **C-35** 作为主责承办人，我希望特殊事件不自动归零余额、完成履行或关闭，以便剩余义务继续跟踪。
36. **C-36** 作为有关闭权限的人员，我希望特殊处理后的义务处置明确并满足正常条件时再关闭，以便不凭事件标签例外办结。
37. **C-37** 作为相关承办人，我希望查看并办理必要的律师委托及阶段关系，以便案件代理与所属委托业务一致。
38. **C-38** 作为相关承办人，我希望查看必要的冻结和联系单关联，以便继续办理关联事项而不复制其业务规则。
39. **C-39** 作为案件使用者，我希望有权限时访问历史和当前附件的有效下载、预览，以便材料可用且不越过业务授权。
40. **C-40** 作为案件使用者，我希望原在途申请只限制其资料和依赖操作，其他合法办理继续在新系统进行，以便不会整体锁案。
41. **C-41** 作为原在途补正人员，我希望退回补正重提沿原审批链完成，以便同一次在途业务只有明确处理归属。
42. **C-42** 作为案件使用者，我希望旧在途结果关联核对后进入新记录且不覆盖新程序事实，以便完整保留过渡结果。
43. **C-43** 作为历史查询人员，我希望原标识、人员、状态、金额、审批及附件关联可追溯，以便新系统准确呈现全部案件历史。
44. **C-44** 作为有专门更正权限的人员，我希望更正已办结历史并留理由、前后值、人和时间，以便不自动重开或触发历史审批。
45. **C-45** 作为集团法务和经办人，我希望完整正常链路及补正、移交、特殊记录和旧在途场景可演示并核对，以便确认首个端到端里程碑。
46. **C-46** 作为评审及维护人员，我希望每个用例有业务结果和验证证据，以便能检查权限、金额、状态及外部效果。

## Implementation Decisions

### 1. 所属模块及最小业务概念

案件办理模块负责案件记录、当前责任和参与关系、程序事实、阶段内进度、审理结案、履行核对和关闭。审批衔接、身份授权、附件及通知经共用能力处理；冻结、律所律师委托和联系单经所属业务模块接口协作。

需要区分的业务概念包括：案件及原标识、主责/经办/协作关系、每次案件业务申请及提交资料、平台实例和处理历史、程序事实与依据、进展和目标计划、审结结果、履行事项及收付、更正和移交记录、附件引用。它们是模型职责，不决定物理表数、主键类型或字段名。

既有多时期案件模型不能按相似名称直接合并。具体字段、当事人类别、编号规则、必填校验、金额口径、程序事实证据类型及历史映射先从真实结构和有效流程核定。本规格不将旧页面选项列作最终状态全集。

### 2. 用例接口职责

| 用例职责 | 输入和前提 | 成功成果与必须阻止的行为 |
| --- | --- | --- |
| 登记/维护案件资料 | 当前有效身份、登记或资料维护操作、核定数据归属与资料 | 保存对应案件；拒绝无权限、范围不符或违反固定提交资料规则的修改 |
| 设置参与关系/移交主责 | 当前有效身份、对应操作与范围、目标人员及关系；移交有原因 | 提交前一位主责；移交即生效且留痕，访问按当前关系重判；目标人员有效性按权威身份核验 |
| 发起/补正立项 | 当前有效身份、发起操作与范围、同一案件、核定资料和当前申请前提 | 固定该次提交并关联平台处理；审批中不替换资料，缺主责/必填或未核清受理结果不得盲目创建另一申请 |
| 核对审批与处理回传 | 已验证的申请/实例/来源关联、结果和历史 | 更新对应申请及有效业务成果；不重复效果，不用迟到结果覆盖新申请/程序事实 |
| 维护程序事实与进展 | 对应操作与范围、案件及核定的事实/依据、进展输入 | 分别保存程序阶段和阶段内进度，不要求内部审批状态替代事实 |
| 记录审结与履行 | 对应操作与范围、审结依据或履行记录、核定金额/期限规则 | 审结和执行完毕分开；保留应收应付及其他义务，不由审结或特殊标签归零 |
| 核对关闭 | 当前有效身份、关闭操作与范围、审结及所需履行已处理依据、关闭理由 | 条件满足才关闭并留记录；有未处理或不明义务、缺授权/依据时拒绝，不新增正常关闭审批 |
| 查询案件、申请、关联和附件 | 当前有效身份、相应查询/访问操作、案件或关联标识 | 返回授权范围内的记录和有效材料；入口隐藏、过去承办或知道标识均不能代替授权 |
| 更正已办结历史 | 当前有效身份、专门更正操作与范围、更正依据 | 记录前后值、理由、人和时间，不自动重开或触发审批；具体可更正字段须核定 |

这是拟实现的高层业务接口职责。HTTP Schema、平台字段、事务/并发策略及错误编码不是已经验证的契约，相关核验后补齐。业务拒绝必须不产生该次无效操作的记录变更或外部效果；外部已受理但本地结果不明则保留为待确认，不伪装成明确失败。

### 3. 授权与责任

- 一人可多角色，按各角色的“操作＋数据范围”成对判断后合并。菜单权限只决定可用入口。查看权、修改权、发起权、移交权和关闭权分别按配置检查。
- 本人范围由当前主责、经办或协作关系确定。其他组织范围与指定/全部范围按对应操作授权判定，不能把查看角色的范围套给修改操作。
- 立项提交前一件案件有一位主责，登记人可不同。设置或维护参与关系属于要核定的操作权限，不因可以查看人员或案件就自动可改关系。
- 有移交操作和相应范围者指定新主责后生效，无新增必须接收或审批环节；记录原/新主责、原因、时间。原主责没有当前关系或其他授权时不自动继续访问，有其他当前授权则照常判断。
- 当前有效身份决定访问，历史经办或审批处理人归属独立保留。账号停用不可继续访问，改名不以姓名重新归属历史。
- 查询、详情、直接接口和附件均执行相应业务授权；关联业务记录还遵守其所属模块授权。

### 4. 登记、立项与每次提交

采用直接登记路径，登记和立项发起由操作权限分别配置。未通过有效立项审批不标记正式立项。立项通过确认内部立项成果，不凭通过结果自动认定法院已受理一审或仲裁。

审批期间固定该次提交资料；必填与固定资料范围必须核定，不能将其扩大为整个案件全部字段锁定。需要修改时先完成平台真实支持的退回或撤回，再补正重提。退回重提保留同一案件和各次申请/处理历史；具体平台是复用实例还是产生后续实例以实测为准，不由本规格假定。

业务决定不继续时保留记录并明确终止；终止操作的权限、与正在运行平台申请的关系须按核定契约执行。不得直接删除历史，或在平台尚未终止时声称平台申请已取消。

### 5. 审批结果与程序事实

| 事件 | 申请与内部业务效果 | 程序/其他效果边界 |
| --- | --- | --- |
| 立项提交已被平台明确受理 | 该次申请进入平台核定的处理中状态，提交资料固定 | 不由此自动认定法院程序或正式立项 |
| 平台可能受理但未获明确回执 | 记录待确认，核对实例后再恢复 | 不当作确定失败立即另建申请 |
| 有效立项审批通过 | 对应申请通过并正式立项，保留结果历史及核定立项成果 | 不覆盖已核实程序事实，不重复生成目标计划等成果 |
| 平台退回或允许的撤回完成 | 该次历史保留，按平台与业务前提允许同案补正 | 不修改既有提交版本，不假定所有业务已终止 |
| 核实法院二审受理等程序事实 | 不改变未完成的内部申请结论 | 按事实更新程序阶段，阶段内进度单独维护 |
| 其他案件申请通过 | 所属业务模块应用该申请有效业务规则 | 不能用一类通用回调把所有申请都当案件完成 |
| 重复或迟到结果 | 保留可追溯处理关联，重复不重复效果；旧结果不覆盖后续有效申请 | 不回退新程序事实，不重复改金额、律师关系、附件或发送通知 |

每次审批状态、程序阶段、阶段内进度分别表达，审结、执行完毕和案件关闭也保留各自含义。示例名称用于验证原则，不定义状态全集；完整程序转换、阶段内进度、哪些业务申请仍需审批及各自结果必须核验。

结果接收须核定平台来源、申请/实例关联、返回确认和重试机制。不能将旧日志已终态的短路当作全业务幂等证据；日志、业务效果及必要通知的重复/部分失败须一起验证。恢复方式在实测契约基础上设计，不预选消息系统或分布式事务。

### 6. 审结、履行与关闭

- 审理结案表示审理结束，执行完毕表示所需履行处理完毕，案件关闭表示业务办结。某次内部结案审批、某一阶段结果或特殊事件标签不能替代整案条件核对；具体事实与状态映射先核定。
- 审结后有履行事项则继续管理应收、应付、已收、已付、剩余义务、期限及其他非金额事项。新记录金额计算采用核定精度与口径；旧成果按原记录和已解释含义保留，不按新规则静默重算。
- 金额余额为零也不能自动证明其他履行事项完成；存在剩余金额、非金额义务或处置不明时保持未办结。异常金额、空值和矛盾标记不能当作默认零或默认完成。
- 有关闭操作且范围适用的人员，核对审结和全部所需义务的完成/处置依据，记录关闭理由及依据后确认关闭，保留处理人和时间。正常关闭不新增审批；无需执行的案件审结后核对办结。
- 关闭时按当前业务事实检查，不能只依据先前页面显示的已完成值。具体并发一致性策略在实现设计中补齐，并以外部可观察的拒绝或正确成果验证。
- 和解、中止、特殊结案等沿用已核实的人工记录、材料和后续安排；相关有效既有审批继续核对。没有追加专门终本、减免、豁免或核销自动流程，未获依据的事件标签不得自动减额、完成履行或关闭。
- 剩余义务未明确处理完毕，主责继续跟进；处置结论明确且满足正常条件后授权关闭。未增加带未处理义务的例外关闭。
- 已办结历史更正不自动重开案件或触发历史审批。新案件关闭后的进一步普通编辑、恢复或重开规则尚未确定，不能从旧反结案方法推断为已授权的新功能；发现有效需求须核实再明确。

### 7. 必要关联能力与试点边界

案件试点需要委托申请、阶段律师关系、必要冻结/联系单信息、身份组织、审批历史、附件访问以及相应用例结果。委托、冻结、联系单各自模块负责本记录、金额及办结；案件通过接口协作，不直接写另一模块内部数据。

具体关联用例按真实测试样本与有效业务核定。委托审批通过不自动视作合同签署或费用结算完成。原有有效费用、评价、冻结期限及联系单成果不能因试点抽样而废弃，完整业务分规格后续继续覆盖。

试点含主诉/被诉或仲裁的代表办理路径，具体各类覆盖由核验确定；尚未核实的再审、协助执行、督办、人民来信等子功能继续列入总规格首期覆盖核对，不在本分规格假装完成全部诉讼能力。

### 8. 历史、附件与旧在途

- 案件主子记录、原标识、状态、人员、金额/时间、审批及附件保留可追溯对照。实际映射按不同历史时期核定，不从 DBML 推断当前物理结构和数据质量。
- 全部案件历史属于最终 PostgreSQL 统一查询目标。已确认办结历史默认只读，专门授权更正留理由、前后值、人和时间；矛盾数据先保留证据并解释，不据旧“关闭”字样自动判定所有义务清零。
- 附件保留业务记录、元数据和实际内容对应及原有有效下载/预览能力，不假设所有来源都可预览或所有 URL 永久有效。元数据迁移与文件来源适配分别设计，访问受业务授权约束。
- 新系统日常办理及新申请；原在途沿唯一旧链完成，补正重提仍沿原链。仅固定对应申请资料和依赖其结果的操作，其他合法进展和程序事实可在新系统维护，不锁定整案。
- 旧在途结果核对实例、提交及业务关联后纳入新记录；只应用所属申请仍有效的业务效果，不用旧结果覆盖新程序事实。旧链所需写入与通知、旧表单依赖和最终退出按实际清单核验。
