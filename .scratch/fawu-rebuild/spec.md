# 法务系统完整重建总规格

Status: ready-for-agent

更新日期：2026-10-22。来源为已确认的决策地图及六阶段路线。本文是首期范围、跨业务规则、交付依赖和验收的总规格，也是分规格索引。

`ready-for-agent` 表示规格已发布，可据此拆分核验与实施任务；不表示运行核验或上线验收已通过。涉及未核实事实的用例，须先完成对应核验再实施。当前仅案件分规格已生成，其余业务分规格后续逐域展开。

## Problem Statement

集团法务和业务经办人需要继续办理完整法务业务，但旧系统架构难以支持新的产品流程和可复用的业务能力，也难以在后续按业务接入 MCP 与 AI Agent。单独改造页面或增加若干查询工具，不能满足本次完整重建目标。

重建同时必须保留现有登录、审批平台、全部法务业务历史及其关联资产。旧源码包含多个时期的业务模型、页面和后台程序；静态实现、导航入口与当前有效业务之间存在未核实差异。若直接照抄旧状态、依赖或表结构，可能延续错误，或破坏历史金额、身份、审批和附件关联。

## Solution

首期重建完整产品、前后端及架构，覆盖十组业务。集团法务统一确认业务范围和有效规则，业务经办人补充实际场景；产品允许调整流程，已经确认的案件新规则优先于旧行为，其余业务以现行有效流程为保留基线逐域核对。

采用 .NET 10 / ASP.NET Core 10、Vue 3 / Element Plus、PostgreSQL，新后端为一个按业务模块组织的应用，主应用部署在内网自管 Ubuntu 24.04 LTS，通过 Nginx 同域提供界面和接口。角色自定义，菜单、操作及对应数据范围分别配置。各模块提供有授权和业务校验的用例接口，供界面及后台作业复用，后续 MCP 场景再基于这些能力规划。

以案件从登记、立项审批到审理结案、履行办结和关闭作为首个端到端验收里程碑，随后完成其余业务及共用能力。测试试用、全部历史对账和恢复演练达标后，联合放行并一次全量正式切换；仅为旧在途申请保留必要旧链，结果核对完成后退出。

## User Stories

以下采用“作为角色，我希望能力，以便业务收益”的用户故事格式。职责名称表示使用场景，不预置同名权限角色；实际角色由授权配置产生。具体业务字段与未确定流程按核验清单补齐。

### 身份、角色与数据范围

1. **G-01** 作为法务人员或业务经办人，我希望沿用公司的统一登录进入新系统，以便继续使用已有身份办理业务。
2. **G-02** 作为具有授权管理权限的人员，我希望创建自定义角色并配置菜单、操作和数据范围，以便按实际职责授予业务权限。
3. **G-03** 作为承担多项职责的人员，我希望同时拥有多个角色，以便不必为每种职责组合新建角色。
4. **G-04** 作为多角色人员，我希望每项操作只合并对应角色授予的数据范围，以便全集团查看权不会扩大本人修改权。
5. **G-05** 作为授权管理人员，我希望支持本人负责或参与、所属组织、所属组织及下级、指定组织、全部数据五类范围，以便配置不同职责的数据访问。
6. **G-06** 作为业务使用者，我希望列表、详情和直接接口对同一操作执行一致的授权，以便访问结果符合角色配置。
7. **G-07** 作为业务使用者，我希望附件、有效导出与报表业务参数遵守对应授权，以便关联入口保持业务数据范围。
8. **G-08** 作为身份未映射或未获业务授权的人员，我希望系统明确拒绝相应业务访问，以便登录成功不会被误认为拥有全部权限。
9. **G-09** 作为业务负责人，我希望人员改名或离职后仍能追溯原经办与操作归属，以便历史记录保持原责任关系。
10. **G-10** 作为业务负责人，我希望禁用人员无法继续访问，以便当前访问与当前有效身份一致。
11. **G-11** 作为业务使用者，我希望“退出统一登录”明确结束法务和统一登录会话，以便理解退出入口的实际效果。
12. **G-12** 作为集团法务负责人，我希望核对实际组织分工和首期角色配置，以便新授权对应真实工作职责。

### 案件与诉讼

13. **G-13** 作为具有案件登记权限的人员，我希望直接登记案件，以便保存待立项案件资料。
14. **G-14** 作为具有立项发起权限的人员，我希望提交前明确一位主责承办人并记录经办和协作人员，以便责任与参与关系可追溯。
15. **G-15** 作为立项发起人员，我希望将案件资料提交既有审批平台，以便审批通过后正式立项。
16. **G-16** 作为案件参与人员，我希望审批期间固定该次提交资料，以便后续能核对实际审批内容。
17. **G-17** 作为立项发起人员，我希望退回后在同一案件补正重提并保留每次申请历史，以便避免重复案件和历史丢失。
18. **G-18** 作为业务决定不再推进案件的授权人员，我希望保留记录并明确标记终止，以便与审批通过后的正式立项区分。
19. **G-19** 作为主责承办人，我希望分别查看案件程序阶段、阶段内进度及各次申请的审批状态，以便准确理解当前办理情况。
20. **G-20** 作为具有相应维护权限的人员，我希望按核实的诉讼或仲裁程序事实更新程序阶段，以便内部审批未完成时也能表达实际程序。
21. **G-21** 作为主责承办人，我希望维护阶段进展、诉讼目标、后续计划与材料，以便继续跟踪完整案件办理。
22. **G-22** 作为具有移交权限的人员，我希望指定新主责后生效并记录双方、原因和时间，以便明确当前责任与交接历史。
23. **G-23** 作为案件使用者，我希望移交后按当前责任、参与关系和角色重新判断访问，以便过去承办经历不自动保留访问权。
24. **G-24** 作为主责承办人，我希望审理结案后继续管理未完成的收付及其他履行义务，以便审结不会提前结束跟踪。
25. **G-25** 作为案件办理人员，我希望保留和解、中止、特殊结案等有效人工记录及依据，以便跟踪特殊事件而不自动消除剩余义务。
26. **G-26** 作为具有关闭权限的人员，我希望核对审结及全部所需履行事项，记录理由依据后确认关闭，以便案件办结有明确条件。
27. **G-27** 作为法务人员，我希望查看案件关联冻结、律师委托、联系单、审批和附件，以便关联信息与所属业务记录保持一致。
28. **G-28** 作为集团法务负责人，我希望核对案件试点以外的有效子功能并安排交付，以便完整诉讼范围不会被首个试点替代。

### 查封冻结

29. **G-29** 作为具有台账权限的人员，我希望维护有效冻结账户和资产明细并关联案件，以便查封冻结记录有明确业务归属。
30. **G-30** 作为法务人员，我希望查看冻结、解封、剩余金额及期限，以便掌握当前资产影响与后续安排。
31. **G-31** 作为承办人员，我希望保留有效主诉、被诉及续封相关流程，以便实际办理环节完整覆盖。
32. **G-32** 作为相关责任人员，我希望按核定的期限规则收到提醒，以便及时处理到期事项。

### 律所、律师与委托

33. **G-33** 作为具有主数据维护权限的人员，我希望维护或同步律所、律师及其有效关联，以便业务使用正确的合作对象。
34. **G-34** 作为具有委托权限的人员，我希望办理合作、案件和投融资委托并关联律师、期间、金额、合同及材料，以便每次委托具备完整业务依据。
35. **G-35** 作为委托经办人，我希望通过既有审批查看委托处理结果及历史，以便按该委托的有效规则继续办理。
36. **G-36** 作为相关法务人员，我希望保留有效费用、结算及评价流程并核对口径，以便审批同意不被误认为费用结清。
37. **G-37** 作为案件承办人，我希望阶段律师关系与对应委托保持可追溯关联，以便重复回传不会重复替换或生成业务记录。

### 清欠

38. **G-38** 作为有权限的清欠经办人，我希望接收事项、变更接收人并保存办理记录，以便责任与进度明确。
39. **G-39** 作为清欠经办人，我希望按有效流程办理退回以及其他移交、解决和退房事项，以便完整清欠流程保留。
40. **G-40** 作为清欠经办人，我希望法务端与明源目标结果一致后才看到回写完成，以便不会把单边成功误认完成。
41. **G-41** 作为具有异常处理权限的人员，我希望看到两边处理结果及待核对事项，并在核对后恢复处理，以便部分成功可以跟踪解决。

### 合同与投融资

42. **G-42** 作为相关法务人员，我希望查询和关联现有合同及框架合同，以便委托与履约有正确合同依据。
43. **G-43** 作为具有重大合同履约权限的人员，我希望维护履约明细、期限和进展，以便跟踪有效合同义务。
44. **G-44** 作为投融资经办人，我希望登记项目并维护进度、尽调、协议和材料，以便保留项目办理全过程。
45. **G-45** 作为相关法务人员，我希望办理项目律师委托及投后履约事项，以便与对应委托、合同和履约结果衔接。
46. **G-46** 作为具有材料访问权限的人员，我希望使用现行有效的合同归档或附件打包能力，以便获取完整业务材料。

### 非诉事务

47. **G-47** 作为综合法律事务经办人，我希望登记事项并使用核定的量化评估规则，以便保留有效成果统计。
48. **G-48** 作为培训事务经办人，我希望记录课程、对象、时间、人员、情况和材料，以便留存培训成果。
49. **G-49** 作为制度、指引或专题经办人，我希望登记分类、名称、内容、成果和附件，以便留存业务成果。
50. **G-50** 作为知识产权经办人，我希望维护专利及其他实际有效类别的登记、状态、期限和材料，以便各类别完整覆盖。
51. **G-51** 作为行政处罚经办人，我希望维护处罚信息、办理进展、结果和收付或执行情况，以便跟踪该事项实际结果。
52. **G-52** 作为其他非诉经办人，我希望按有效类别登记经办、事项说明及材料，以便保留其他实际业务。
53. **G-53** 作为集团法务负责人，我希望分别核对各类非诉字段、流程和成果，以便不将所有类别套入一个未经确认的统一模型。

### 法律事务与联系单

54. **G-54** 作为具有申请权限的人员，我希望登记法律事务或联系单并发起既有审批，以便启动对应业务协作。
55. **G-55** 作为协办人员，我希望查看本人相关事项、阅读状态及办理进展，以便继续承担协作职责。
56. **G-56** 作为联系单经办人，我希望申请同意后按有效规则继续协办，以便申请通过不会被误认办结。
57. **G-57** 作为有验收发起权限的人员，我希望提交办理成果并进行既有验收审批，以便验收结果与事项完成相符。
58. **G-58** 作为法务人员，我希望区分一般法律事务、诉讼联系单和法务联系单的有效规则，以便每类业务正确结束。

### 绩效与重大业绩

59. **G-59** 作为申报人员，我希望登记成果、参与人员和比例，以便按核定周期进入业绩处理。
60. **G-60** 作为有初评权限的人员，我希望显式完成初评并保留记录，以便评分状态对应实际操作。
61. **G-61** 作为有复核权限的人员，我希望显式完成复核并保留记录，以便复核与草稿保存区分。
62. **G-62** 作为兼有两种评分权限且范围适用的人员，我希望分别完成初评和复核，以便遵循已确认的兼任规则。
63. **G-63** 作为相关负责人，我希望按核定公式汇总业绩和绩效，以便有效业务口径可解释、可对账。

### 文件、知识与报表

64. **G-64** 作为有权限的法务人员，我希望从新法务进入现有文件与知识应用，以便继续使用已有平台能力。
65. **G-65** 作为有权限的法务人员，我希望访问制度、工具、判例等实际有效知识入口，以便已有知识资产继续可用。
66. **G-66** 作为有报表权限的人员，我希望通过正确业务参数查看现有报表，以便结果保持有效口径和数据范围。
67. **G-67** 作为业务负责人，我希望核对更换数据库后的报表来源、口径与样本差异，以便报表不会因迁移静默变化。

### 共用能力、历史与切换

68. **G-68** 作为业务使用者，我希望附件元数据、业务记录和实际文件继续关联，并保留原有有效下载与预览能力，以便材料可查且受业务授权控制。
69. **G-69** 作为有相应权限的人员，我希望使用实际有效的分享和导入导出流程，以便现行协作能力保留且不扩大授权范围。
70. **G-70** 作为责任人员，我希望收到有效站内及外部提醒、通知和日历信息，以便业务安排延续。
71. **G-71** 作为系统维护人员，我希望按实际启用清单接管同步和提醒作业，以便新旧不会无意重复写入或发送。
72. **G-72** 作为业务申请人员，我希望回执不明时看到待确认并先核对平台实例，以便不盲目另建重复申请。
73. **G-73** 作为业务使用者，我希望重复或迟到回传保留历史且不重复产生业务效果，以便当前业务结果正确。

## Implementation Decisions

### 1. 规则来源与实现前提

- 用户最新确认的产品规则和有效架构决策优先。已被更正的 SQL Server 新业务库选择不再生效；PostgreSQL 是当前目标。
- 现行有效流程作为其余业务保留基线。源码中的错误、注释、未启用入口和未核实行为不自动成为需求，也不能据抽样不足删除已确认范围。
- 每个待核验事项记录来源、影响用例、责任职责和通过条件。字段、流程或平台事实先核定，再完成依赖它们的契约与实现；新产品取舍确实出现冲突时单独记录决定。
- 不把旧平台文档示例中的内部地址、秘密值或操作说明当成运行配置和用户授权。

### 2. 运行与模块结构

- 后端 .NET 10 LTS / ASP.NET Core 10；前端 Vue 3 / Element Plus；业务库 PostgreSQL；Ubuntu 24.04 LTS + Nginx 同域托管。具体补丁、数据库和驱动版本、数据访问方式、资源与备份方案须核验锁定，尚未选定 ORM。
- 一个后端应用按业务模块组织。业务模块负责本模块记录、状态、金额、办结与用例校验；其他模块经接口协作。职责分组不要求各自成为项目、数据库或独立服务。
- 共用能力承接身份组织映射、角色授权、附件、审批协议、通知及作业运行；提醒条件和审批的业务效果由所属模块决定。
- 优先直接适配既有平台。仅实测证明必须依赖 Windows / .NET Framework 时采用隔离过渡进程，并明确调用权限、失败恢复和退出条件。当前并未证明需要该进程。

### 3. 业务用例接口与授权

| 接口职责 | 输入语义 | 必须保证的外部行为 |
| --- | --- | --- |
| 查询业务及关联 | 当前有效身份、查询条件或业务标识 | 查询范围来自该查询操作对应的角色授权；详情、汇总和关联记录执行各自业务授权 |
| 执行业务操作 | 当前有效身份、对象标识、业务输入及当前操作前提 | 所属模块检查操作与范围、状态和已核定业务规则；无权限或前提不成立不得修改记录或发起外部效果 |
| 提交或核对业务申请 | 当前有效身份、所属业务、该次提交资料及申请关联 | 固定该次提交资料；受理不明先待确认并核对，不盲目创建另一实例 |
| 处理平台结果 | 已核验来源及平台实例、申请关联、结果和历史 | 将结果交给所属业务模块，防重复和迟到覆盖；审批状态与业务成果分别表达 |
| 获取附件及外部入口 | 当前有效身份、附件或业务关联、所需访问操作 | 检查对应业务授权及平台访问能力；不能靠隐藏菜单代替服务端校验 |

上述是业务契约职责，不是已完成的 HTTP 字段 Schema。具体请求响应、错误约定、实例关联、并发与恢复策略在对应分规格或核验中补齐，不预设路由、缓存、消息中间件或分布式事务。

多角色授权按“操作与该角色数据范围”成对判断，再合并允许结果。菜单权限合并为入口，但菜单可见不能替代操作和数据授权。本人范围依据当前主责、经办或协作关系；组织范围依权威组织关联核定，不照搬旧字符串包含匹配。

身份认证由既有统一身份平台负责，新法务配置业务授权。历史归属与当前访问分开：改名或离职不改写原责任记录，禁用人员不可继续访问；未知身份映射或未授权不开放对应业务访问。

### 4. 业务模块的效果边界

| 模块 | 负责的主要规则 | 协作边界 |
| --- | --- | --- |
| 案件办理 | 直接登记、正式立项、当前责任、程序事实与进度、审结、履行和关闭 | 审批申请独立；关联冻结、委托及联系单保留所属模块规则 |
| 查封冻结 | 台账、账户资产关联、金额、期限及有效续封/解封规则 | 向案件提供关联和提醒依据，不在案件界面另写一套金额规则 |
| 律所律师与委托 | 主数据、各类委托、阶段关系、有效费用和评价 | 审批同意不等于合同签署或费用结清；委托与案件/项目/合同保持关联 |
| 清欠 | 接收、人员变更、退回等有效办理与两边结果一致 | 单边成功或结果不明为待核对/异常，保留两边结果，核对一致才确认完成 |
| 合同与投融资 | 现有合同关联、项目、尽调、重大合同及投后履约 | 委托经所属模块办理，外部合同来源与实际履约规则先核定 |
| 非诉事务 | 各类别有效记录、状态、金额、期限及成果规则 | 保留类别差异，不预置万能表或统一审批、办结条件 |
| 法律事务与联系单 | 申请、协作、阅读和进展、验收的有效规则 | 已证实的法务联系单申请通过后仍待协办，验收通过才办结；其他类别须逐项核验 |
| 绩效与重大业绩 | 申报、比例、初评、复核和有效汇总口径 | 评分操作分别授权且留记录，允许同人兼任，不复制普通保存即自动完成评分的隐式行为 |
| 文件知识与报表入口 | 法务端入口、业务参数、对应授权和有效口径 | 外部文件知识/报表平台本体保留，外部接口和数据来源须真实验证 |

案件三类状态、正式立项、责任移交、关闭和特殊处理的详细规则以案件分规格为准。其余组在核定全部有效子流程后编写分规格，不能从代表路径推断整组完成。

### 5. 身份与既有平台

- SSO 对接文档明确授权码流程，但不证明 OIDC、PKCE、永久唯一人员标识或完整组织 Schema。当前注册、属性开放、回跳、令牌和退出能力须验证；不因文档存在视为接入完成。
- 退出入口明确“退出统一登录”，按已确认的浏览器前台统一退出与本地会话销毁链路适配；其他应用实际影响、回调及回收授权契约须核验。
- 新法务登记、发起、查看审批状态、结果和历史，提供跳转；审批人仍在既有审批平台办理，保持其路由及办理规则。
- 每次申请关联业务、提交资料、平台实例和处理历史。退回补正重提按平台实际支持动作执行，不能自行模拟平台撤回或取消成功。
- 平台可能受理而回执不明时待确认；先核对实例再恢复处理。重复结果不重复变更业务明细、关联、金额或通知；旧申请迟到结果保留历史但不得覆盖新申请或已核实的程序事实。
- 文件、报表、明源和通知平台本体保留，由新法务重做必要入口及集成。平台参数、权限、失败及恢复以真实契约为依据。

### 6. 数据、附件与新旧办理归属

- 全部法务业务历史及关联信息最终进入 PostgreSQL 并由新系统统一查询，允许分阶段迁移。不要求搬迁外部组织、审批、文件平台的数据库或全部文件内容。
- 核对主记录、子记录、原标识、人员组织历史、审批材料/实例/历史、附件、有效消息与操作记录等资产。新模型可改变，旧模型的多种标识和时期差异须有可追溯映射，不能按同名对象直接合并。
- 金额精度、舍入、空值、时间与时区、中文排序/搜索、分页及报表语义须对账。不能只替换连接字符串、按新规则重算历史或凭总行数确认保留。
- 附件元数据与实际内容分别核对；保留来源、业务关联和原有有效下载/预览能力，平台或本地存储适配另行核定，不假设所有旧 URL 永久有效。
- 已确认办结历史默认只读，专门授权更正并记录理由、原值、新值、处理人与时间；不自动重开或触发历史审批。矛盾旧状态保留证据后核定映射，不静默猜测。
- 新系统负责切换后的日常办理和新申请。原在途沿唯一旧链完成，补正重提仍沿原链；仅限制该次申请资料及依赖其结果的操作，其他合法业务在新系统继续。旧结果经关联核对进入所属模块，不覆盖新程序事实。
- 旧链仅为原在途及必要通知保留；根据剩余实例、结果、回传和写入者核对后退出。普通业务、同步和通知的接管须明确执行归属，避免无意双写和重复发送。

### 7. 交付依赖与正式切换

| 阶段 | 必须交付 | 通过条件 |
| --- | --- | --- |
| 1 规格与事实核验 | 本总规格、案件分规格、核验记录，以及逐域有效覆盖与角色职责 | 影响用例的实际字段、状态、平台和数据事实明确；缺口有影响与依赖，不填成既定规则 |
| 2 必要底座与历史小样 | 可运行技术组合、必要授权和平台适配、代表历史映射 | 版本/部署验证、真实身份与审批/附件适配、操作范围配对和历史小样对账通过 |
| 3 案件完整链路 | 案件主流程与必要关联能力 | 案件分规格正常/异常验收通过，业务确认，作为首个端到端里程碑 |
| 4 其余业务逐域完成 | 各域分规格、完整有效用例和剩余共用能力 | 按实际依赖实现并逐域验收；保留规则对照旧环境，改变规则按新规格验证 |
| 5 全历史、试用与演练 | 全资产对账、异常清单、完整试用、任务接管与备份恢复演练 | 正式验收矩阵覆盖十组及集成/后台，关键异常解决，其余原有异常逐项确认，实测维护与恢复时长 |
| 6 一次正式切换及旧链退出 | 联合放行、维护窗口最终同步、全量切换验证、旧链逐项退出 | 法务/开发/IT 各自确认后由 IT 执行；增量与外部结果可恢复，剩余旧链有核对及退出证据 |

实际实施任务按用例和真实依赖拆分，前阶段已有共用能力可复用；不得将“案件先完成”改成首期只交付案件。年底是期望时间，人员投入、规模和演练明确后才估算工期。

允许维护窗口暂停用户新增、编辑与发起申请，最终同步核对后恢复；审批平台办理、回传和查询安排分别确定，不假设外部停机。关键故障先暂停新写入，核对保留新增修改及外部已受理结果，优先恢复新系统；不要求旧系统全面接管新业务，不以还原本地数据库替代对外部效果的核对。

## Testing Decisions

### 验证入口与先例

主要从业务模块的用例接口验证外部行为：有效身份与输入条件进入，观察授权结果、业务状态、金额、关联及外部效果。不通过私有方法、内部类组织或一比一复制实现逻辑来证明功能。

案件试点还须走关键 UI，真实 SSO、审批、文件、明源、报表和通知适配另有契约贯通验证。测试替身可验证失败、防重复等应用行为，但不能代替真实平台和迁移演练。接口授权与附件访问的预期沿用已经确认的案件验收基线，无需重新采访。

旧工程静态调查及本次项目文件检索未发现可直接继承的自动化测试项目；不编造旧测试框架或成功结果。旧 Windows 测试环境、原源码和经核对的业务样本是保留行为对照来源；已确认改变的行为以新规格为准。

正式切换需十组逐域记录与上述跨域验证，集团法务统筹业务与历史例外，经办人验证实际场景，开发负责代码评审和技术验证，IT 负责部署、数据库、备份恢复及切换演练。关键金额、义务、身份权限、在途审批和必需材料问题阻断；迁移新产生的丢失、损坏或错误必须修复。
