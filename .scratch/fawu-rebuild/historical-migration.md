# 历史资产迁移与过渡基线

关联事项：[确定历史数据、附件和在途业务保留方案](issues/09-historical-data-attachment-migration.md)。更新日期：2026-10-22。迁移目标、在途控写、维护窗口与历史更正规则已确认；本轮没有连接数据库或执行迁移。

## 已确认的迁移目标

全部法务业务历史记录及关联信息最终迁入 PostgreSQL，新系统统一查询。允许分阶段，保留外部平台本体；历史人员归属、审批历史、业务与附件关联不能因更换引擎消失。决定详情见关联事项的 Confirmed decisions。

旧在途审批可沿原处理链完成，新申请走新系统；每次申请只能有一条处理链，旧结果关联核对后进入新业务记录，不能覆盖已核实的新程序事实。维护窗口可暂停用户新增、编辑和发起申请，具体时长演练后确认；审批办理与回传接收单独安排。

## 资产与核验输入

| 资产 | 已有事实与保留目标 | 需从环境核实的输入 |
| --- | --- | --- |
| 业务记录与子记录 | 旧 DBML 同时存在多组案件模型、整数 ID 与 GUID 关联；需保留可追溯的原标识与关联，不凭同名对象合并或丢弃历史 | 实际表结构、各时期状态、记录量与增量、空值、重复标识、孤儿记录、删除标记及 JSON 可解析性 |
| 金额、日期及报表 | 按原记录及已确认业务含义对账，转换需可解释；更换数据库不等于按新规则重算旧成果 | 精度、舍入、时间/时区含义、中文排序搜索、SQL/存储过程/触发器与外部报表依赖 |
| 人员与组织 | 历史经办及操作归属保留，当前访问按有效身份、授权与参与关系判断 | 旧登录名、人员 ID、部门 ID 与新身份的对照；改名、离职和组织变化样例，不只用姓名匹配 |
| 审批实例与材料 | 旧日志 ID、业务 GUID、平台实例、提交材料和历史相互关联；在途处理归属与新申请分开 | 在途实例清单及状态、回传与旧表单依赖、退回重提、重复/迟到结果、旧链剩余写入者及退出依据 |
| 附件元数据与文件 | 保留业务关联、来源类型、文件原文及原有有效下载/预览能力，访问沿用业务授权；元数据与实际内容分别核对 | OA、uploadLite、旧本地文件的数量、完整性、大小类型、下载/预览能力、临时 URL、权限及缺失清单 |
| 后台作业 | 明确旧新同步与通知的运行责任，避免无意并行写入或重复发送 | 实际启用的任务、账号、参数、调度、最近运行结果及外部依赖；代码分支不等于已启用 |

来源：[旧资产与集成静态研究](research/preserved-integration-contracts.md)、[PostgreSQL 迁移门槛](research/postgresql-compatibility-followup.md)。当前没有真实规模或缺失率数据，不按源码推算迁移时长与维护窗口。

## 附件与异常核验边界

旧附件存在外部平台与本地文件多种来源，不假定全部文件都搬入数据库或全部旧 URL 永久有效。新业务库迁移与文件内容的存储适配分别设计，文件平台本体继续保留。

旧预览方法可能上传本地文件并回写附件元数据，所以后续验证须在可恢复的隔离测试副本进行，不能把预览当作纯读取生产数据。核验保留业务字段、附件记录与实际文件的对应关系，不能仅凭元数据数量确认附件保留完成。

发现缺失、冲突或无法解释的旧值时保留原始证据并形成异常清单，不静默丢弃或猜测转换。具体异常处置由集团法务确认业务含义、经办人补充材料，IT 与开发处理技术修复；验收是否允许带明确异常切换由后续切换事项决定。

## 在途办理与历史更正（已确认）

- 按在途申请限制审批资料及依赖审批结果的操作，其他业务在新系统按权限和合法状态继续办理，不锁定整个案件或事项。补正重提沿原链；新系统负责日常办理，旧链仅承接原在途申请，结果关联核对后纳入新记录。
- 已确认办结历史默认只读；专门授权更正，保留理由、原值、新值、处理人和时间。更正不自动重开案件或触发历史审批；旧状态存在矛盾的记录保留原证据并核验后映射。

切换、回退、后台任务接管和最终验收条件由[完整业务验收与新旧切换](issues/10-cutover-acceptance.md)继续确定。本记录是规划输入，不是可直接执行的迁移脚本或运行验证报告。
