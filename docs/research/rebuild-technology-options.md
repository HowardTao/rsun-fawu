# 法务系统完整重建：.NET 技术候选与接口复用条件

研究日期：2026-10-21（Asia/Shanghai）。对应决策任务：**研究重建技术候选与业务接口复用条件**。

本报告为候选比较，未作技术选型决策。用户已明确：首期全面重建产品和架构、覆盖完整业务；现有登录、审批平台及历史数据必须保留；MCP 与 AI Agent 的具体协同场景后续再讨论。旧系统有 Windows 测试环境，新部署环境、数据库要求和团队能力尚未确定。

## 结论与有限候选

建议优先比较“现代 ASP.NET Core 业务核心”的两条产品路线；若既有登录或审批 SDK 无法直接适配，再评估隔离旧集成的过渡方式。这个建议是基于本工程约束的判断，不是用户已确认的架构。

| 候选 | 产品与业务结构 | 适用条件 | 需要付出的代价与验证 |
| --- | --- | --- | --- |
| A：ASP.NET Core + 独立 Web 前端 | 业务用例集中在服务端业务模块；新前端通过应用 API 访问。前端框架另选。 | 团队具备前后端交付能力，产品需要较复杂的交互，或确有独立发布需求。 | 要维护前后端契约及两套工具链；核实同域或跨域登录、会话与授权边界。是否拆部署并非由“前后端分离”自动决定。 |
| B：ASP.NET Core + .NET Web 界面 | 同一业务核心由 MVC/Razor Pages 或经验证的 Blazor 界面调用。具体界面方式另选。 | .NET 团队能力较强，希望先控制交付链复杂度；能满足重建后的产品交互要求。 | 页面代码仍需调用明确的业务用例，避免业务规则重新散进 UI 事件；Blazor 的运行模式、组件兼容与交互体验需要另行验证。 |
| C：A 或 B + 隔离的旧集成桥接 | 新产品和业务核心完整重建；必要时让 Windows 进程或旧应用承接暂时无法迁移的登录、审批 SDK 调用。 | 实测确认有 Framework/Windows 限制，而平台又必须保留；组织允许这种部署及对旧集成的改造。 | 增加网络依赖、部署和故障处理责任，必须明确调用权限、超时、重复提交与桥接退出条件。它是过渡部署选择，不代表首期只做查询或保留旧产品界面。 |

三条路线均应先明确业务模块边界、身份与组织范围、业务状态以及对外集成契约。当前没有证据要求微服务、消息总线或更换数据库，不将这些设为默认前提。

## 已核实的官方技术事实

### .NET 支持期

微软支持页本次抓取的表格列出以下状态；支持政策覆盖 .NET 运行时、SDK、ASP.NET Core 与 EF Core。[S1]

| 版本 | 本次官方表格的阶段 | 支持结束日 | 对本工程候选的影响（判断） |
| --- | --- | --- | --- |
| .NET 10 LTS | Active | 2028-11-14 | 当前更值得优先评估的现代重建基线，仍需验证企业 OS、组件与运维要求。 |
| .NET 9 STS | Maintenance | 2026-11-10 | 支持窗口接近结束，不宜直接作为长周期重建的默认起点。 |
| .NET 8 LTS | Maintenance | 2026-11-10 | 同样即将结束支持；“LTS”字样不能代替检查剩余支持期。 |

官方政策要求在支持期内保持最新补丁；自包含发布也需要应用方更新随应用携带的运行时。[S1] 本报告不把支持期表等同于某个企业操作系统版本已获支持，也没有核定旧 .NET Framework 4.6.1 的具体宿主支持状态。

### System.Web、WebForms 与现代 .NET 的边界

- 微软明确说明 WebForms 随 .NET Framework 提供，是 Windows 专属组件，不会移植到 .NET Core；不能通过把目标框架改为现代 .NET 就让旧 `.aspx` 页面及服务器控件继续运行。[S2]
- ASP.NET Framework 到 ASP.NET Core 的迁移需要处理 `System.Web`、会话、认证授权、HTTP 请求管线和依赖库兼容差异。微软为生产系统列出增量迁移及原地迁移路线，而不是承诺整个应用可直接升级。[S3]
- System.Web adapters 的远程认证能让 Core 应用向旧 ASP.NET 应用请求已认证的 `ClaimsPrincipal`；它要求两应用同时运行和相应配置。它不等于实现完整 WebForms 页面兼容。[S4]

因此，本工程的旧页面、业务规则与第三方程序集要分别判断“重新实现”“迁移源码”“保留受控集成”。程序集能被引用或编译，并不足以证明实际调用在现代运行时及目标 OS 上可用；兼容性实验要以真实调用结果为准。

### Windows 与 Linux 部署

ASP.NET Core 官方部署文档列出 Linux 上的 Nginx，以及 Windows 上的 IIS/Windows Service 等托管方式；发布结果既可依赖服务器运行时，也可携带运行时。[S5]

这说明现代业务核心有不同部署候选，不能证明本工程整体已经跨平台。WebForms 的 Windows 限制是已核实事实；现有审批 SDK、SSO 组件、文件路径、数据库驱动、原生依赖及网络认证是否形成额外 Windows 限制，仍须核实。[S2][S5] 已有 Windows 测试环境是验证资源，不自动决定新系统生产部署选择。

### 数据库与历史数据

EF Core 通过 provider 支持不同数据库；官方要求核对 provider 的质量、许可、支持及版本兼容，并提醒 provider 通常不能跨 EF Core 主版本直接使用。[S6] 本次列表中，微软 SQL Server provider 的数据库范围写为 SQL Server 2012 及以上，EF Core 列为 8、9、10；这是 provider 列表信息，不是对旧数据库服务器仍受厂商支持或本工程可无损迁移的保证。[S6]

本工程旧数据访问据已知项目情况使用 LINQ to SQL；这不意味着选 EF Core 后原有映射、查询语义或存储过程调用会自动兼容。本次未运行旧系统、未连接数据库，也没有确定采用 EF Core 或更换数据库。至少要先核定：

- 数据库实际产品、版本、兼容级别、排序规则及企业允许的升级范围；
- 主键、历史状态、组织/人员关联、审批实例与业务记录关联；
- 存储过程、触发器、默认值及报表计算中承载的业务规则；
- 附件存储位置和访问权限，以及哪些历史记录仍可能更新。

保留历史数据可以有多种实现，不等于必须原样保留表结构，也不等于可以默认一次性导入新库。具体方案需要迁移决策任务确定。对于同时运行的新旧系统，必须先确定每类数据的写入归属和冲突处理；本报告不默认双写。

## 保留登录与审批的适配前提

### 现有登录

“保留登录平台”与“原封不动沿用 System.Web 登录代码”是两个不同层面的要求。官方认证迁移文档区分：重新实现 Core 认证适配、通过旧应用远程认证、以及共享 OWIN Cookie。共享 Cookie 需要旧应用确实使用 `Microsoft.Owin` Cookie 认证，并匹配 Cookie 配置和数据保护设置；不能据现有登录 Cookie 的存在就认定可共享。[S4]

用户已提供独立 SSO 对接文档：`/Users/tony/Documents/工作/竹云统一身份认证oauth集成指南v1.1.8.doc`，并明确后续再接。本轮未读取该文档，也不依据文件名断言协议或现代 .NET 兼容性。旧代码中的接入方式也不自动成为新系统的接入要求。后续身份任务应核对文档、服务注册、回调与退出机制、证书信任、用户唯一标识及组织权限来源，再通过运行验证确定适配方式。认证成功还需要映射到业务授权；当前浏览器登录不能自动等同未来 Agent 的委托身份。

### 现有审批平台与 SDK3

本次没有获得现有审批 SDK3 的厂商支持矩阵或版本对应官方接口契约。不能由“旧系统能运行”推断 DLL 可直接运行于 .NET 10 或 Linux，也不能由 SDK 名称推断它使用 REST、SOAP、COM 或特定身份委托方式。

后续集成任务应依据已有接口研究和测试环境，验证受支持的运行时/OS、入口身份、流程实例及业务记录关联、状态查询、审批回传、附件和重复提交处理。如果厂商提供经验证的现代 HTTP 接口，可评估直接适配；若仅旧 Framework SDK 可用，再比较候选 C。以上是适配条件，不是替换审批平台的计划。

## 为未来 MCP 留下业务复用条件

MCP 官方 C# SDK 的 README 说明：`ModelContextProtocol.Core` 提供底层能力；`ModelContextProtocol` 提供 hosting/DI 扩展；HTTP 服务使用 `ModelContextProtocol.AspNetCore`。[S7] 它证明现代 .NET 有官方接入工具，不证明旧 WebForms 业务会自动变为 MCP 能力。

本次读到的是官方仓库动态 `main` 的 README 快照，未锁定 NuGet 发布版本；SDK 项目目标框架文件抓取超时，故最低 TFM、特定 .NET 版本兼容性及依赖组合仍需在未来接入时按选定包版本核验。不把 README 当作稳定版本支持承诺。

现在可纳入重建的复用条件是：业务用例通过明确的输入输出调用，显式获取用户和组织上下文，统一执行授权、业务校验、状态转换和审计；登录及审批的第三方模型经适配后进入业务模块。前端、后台任务和后续 MCP 入口复用这些用例，避免业务规则绑定在页面或 MCP 工具内部。此为架构判断，本轮不设计 MCP 工具、工具权限或 AI 场景。

本次核对的 MCP **2025-06-18** HTTP 授权规范要求使用相应 OAuth 授权机制、面向资源的令牌校验，并禁止把收到的客户端令牌原样透传给下游 API。[S8] 这是明确版本的规范基线，本次未确认它是截至 2026-10-21 的最新协议版本。现有 SSO 身份是否以及如何映射到未来授权流程，须在未来场景与协议版本确定后设计，不预设两者可互换。
